# 启动器、GM 与资源工具的交互对照

当前 Go 版通过自有多人启动器接入解压客户端。除了频道与游戏 TCP，原项目还有命令行、进程就绪文件和 GM 本机管道。各入口的迁移状态如下。

| 调用方 | 旧接口约定 | 当前核对结果 |
| --- | --- | --- |
| 解压客户端的 `Start-Client.ps1` 和 `LocalTools/DNF100Launcher.exe` | 在玩家电脑读取配套启动配置并连接固定本机端口。频道 7001，城镇 10019，自由决斗 10501，排位 10252，洞察 10063。 | 自有启动器绑定五个原端口，再经 TLS 连接指定账号。实际用原脚本执行 CheckOnly 和 PrepareOnly，并用正式 Go 端口收取原始应答。[测试记录](../go-server/tools/multiplayer/README.md) |
| 源码树与发布包的服务管理器 | 读取 `runtime/next-ready.json`，核对运行进程、Windows 启动时刻和宿主版本。 | Go 在所有端口绑定后原子写入原字段 `Schema`、`ProcessId`、`StartedUtcTicks`、`HostPath`、`HostSha256`、`RunId`、`ServerEventsPath`、`LocalEntry`、`LocalGmCommands`、`NativePartyNotices`、`NativeTownProfile140`、`ChannelPort`、`GamePort`，并保留开发脚本读取的 `go-ready.json`。LauncherUI 检查 Go 原生二进制实际映像及哈希，默认发行路径为 `Server/artifacts/bin/serve100/release/serve100.exe`。[Go 凭据](../go-server/cmd/serve100/lifecycle.go) · [工具兼容补丁](../go-server/tools/legacy-launcher.patch) |
| 旧 Host 命令行与批处理 | 服务启动接受 `--root`、`--run-id`、`--bounded-console`。另有 `--request-stop`、`--prepare-client`、`--check-inputs`、`--evidence-root` 和 `--create-release-database`。 | 停止命令沿用 `Outcome=StopRequested`、绝对 `Path` 和五字节停止文件。客户端准备核对就绪进程及原启动器或完整关联的源码工具包，输出 `Outcome`、`Launcher`、`Project`、`Client`、`ProcessId`、`ClientUI`，桥接配置留在 `runtime/client-launch`。预检返回 `InputsVerified` 或 `InputPreflightFailed`，只读校验原证据清单、文件哈希和 Go 资源导出。[客户端准备](../go-server/cmd/serve100/lifecycle_client.go) · [预检](../go-server/cmd/serve100/lifecycle_preflight.go) |
| 发布打包和数据库种子 | 生成一个含 `local` 初始账号及 1,000,000 点券的空 SQLite 数据库，并输出 `Account`、`Cera`、`Characters`、`Policy`、`SHA256`。 | Go 命令输出相同字段，对应新写入的 `runtime/data/release-seed.sql` 实际哈希。种子来自服务端正在使用的 PostgreSQL 迁移，应用时在事务内要求目标还没有 `s9a1` schema。发布脚本生成配套工具、文件清单和 ZIP，打包过程不访问数据库。[离线种子](../go-server/cmd/serve100/lifecycle_seed.go) · [打包入口](../go-server/tools/publish.ps1) |
| 源码构建、同步与停服备份 | `BuildRun` 复验源码和二进制。`SyncOrigin` 在实际 Git 源码根处理已检查的提交。`StoppedDataBackup` 在生命周期锁内两次核对已有 `Work` 子目录的停服备份。 | Go 源码树使用本地 `go.ps1` 生成候选，只有源码身份和编译一致时才替换实际程序。Go 发布包复用配套程序和 UI，并不显示 Git 同步。`StoppedDataBackup` 核对 PostgreSQL 归档 SHA-256、部署源码或二进制身份、实际连接目标及当前 `s9a1` / `s9a1_import` 逻辑数据。[脚本](../go-server/tools/launcher-runtime.ps1) · [存档归档工具](../go-server/tools/postgres/save_archive.py) |
| 诊断工具与原捕获脚本 | 源码工具按 `RunId`、`ServerEventsPath` 和配置的帧记录路径读本地 JSONL。 | 通用运行日志按 RunId 保存。帧观察通过 `Diagnostics:FrameMode` 或 `SERVE100_NEXT_DIAGNOSTICS__FRAMEMODE` 显式启用 `metadata` 或 `full`。默认关闭应用帧记录。频道交换和游戏引导身份正文保持遮盖。原捕获脚本读取同名 JSONL 字段。[帧记录](../go-server/cmd/serve100/lifecycle_frames.go) |
| LauncherUI 发金币、点券和邮件 | 原 UI 调用 `--gm-wallet <GUID>` 或 `--gm-mail <GUID>`，传 `--root`、`--account local`、`--character`、`--reason`，另传 `--cera`、`--gold` 或 `--template`、`--count`。独立 `--gm-cera` 用 `--operation-id` 传操作号。原服务通过限当前系统用户的命名管道提交到游戏会话。 | 旧 UI 按源码固定发送账号 `local`。多人游戏凭据绑定实际玩家。Go 提供同名的 Windows 当前用户管道，授权钱包、单独点券、邮件和智慧补给均通过角色会话落库。离线邮件沿用 runtime/gm-mail-outbox，队列和最终回执已用轻量本地样本核对。原 UI 的跨进程及数据库联验安排在逻辑迁完后。[原 UI](../s9a1/ClientTools/LauncherUI/Program.cs) · [原操作入口](../s9a1/Server/src/Serve100.Host/LocalGmOperatorService.cs) · [邮件](../s9a1/Server/src/Serve100.Host/LocalGmOperatorService.Mail.cs) |
| GM 目录生成工具 | `--gm-index --client <目录> --output <文件>`，可附 `--server-root`。输出使用 camelCase，顶层字段为 `version`、`generatedUtc`、`clientPath`、`pvf`、`imagePacks2`、`database`、`items`、`ready`。旧版直接从本地 SQLite 读取角色列表。 | Go 版读取匹配资源的完整物品名称索引，按原字段输出客户端资源和文件统计。从指定 PostgreSQL 按本机账号读角色列表，database.fileCount 和 bytes 保留对历史 SQLite 文件的实际统计。老界面实机对接待验收。[旧索引生成器](../s9a1/Server/src/Serve100.Host/GmClientIndexCommand.cs) |

原 GM 回复的字段顺序和命名可从 `LocalGmOperatorReply` 核对。包括 `Status`、`OperationId`、`Reason`、`CurrentCera`、`Grant`、`CharacterRevision`、`AccountRevision`、`ReadBack`、`CurrentGold`、`WalletGrant`、`WisdomSupply`、`CurrentFatigue`、`MailGrant`。迁移时用同一操作号重放，核对返回 JSON、账号和角色的版本及资产落库结果。[回复定义](../s9a1/Server/src/Serve100.Host/LocalGmOperatorService.cs)

通过在线账号租约和 GM 权限校验的 C176 `//item` 可按需准备单个物品及其关联资源。准备完成后一次发布新目录，受理中的其他请求沿用各自已有的快照。GM 邮件可以按需读取未准备的普通附件定义。[在线物品准备](../go-server/internal/host/gm_catalog.go)

游戏连接检测到对端断开或接收出错时立即取消会话，停止分派已排队的请求，再等待读取协程退出并释放当前账号租约。同账号的新连接在旧连接收尾后取得新租约。[连接生命周期](../go-server/internal/host/server.go)

在本项目的解压客户端上，Go `--gm-index` 实际输出 292,895 条物品，其中装备 212,485 条、可堆叠物品 80,410 条。ImagePacks2 扫描到 9,751 个文件，共 21,639,464,113 字节。命令优先使用匹配的预生成索引，也能直接读取随客户端提供的原始 PVF 和所需外部 profile，生成可复用的 `item-index.json`。使用已有物品缓存再次生成完整索引用时 2.15 秒，产出 45,159,830 字节。缺少可用数据库连接时，角色数组为空，物品索引仍可打开。管理页面由本机 WebView2 加载。[Go 索引命令](../go-server/cmd/serve100/gm_index.go)

## Windows 发布

从 `go-server` 目录执行 `pwsh -NoProfile -File .\tools\publish.ps1`，默认使用项目内已导出的 `.work/catalog/characters.json` 和匹配的外部 PVF。ZIP、清单和构建缓存都落在项目内。委托旧工具的兼容补丁已经按原源码 ZIP 校验，发布脚本会判定原脚本是否已应用补丁。首次启用发布包时，将 SQL 种子手动应用于准备好的空数据库，再在服务实例的 `runtime/postgres-dsn.txt` 保存该库的连接字符串。也可用 `S9A1_POSTGRES_DSN` 指向已有迁移库。发行内容不包含私有连接字符串或玩家数据库。

源码树通过 `s9a1/Tool/Local-Run.ps1 -Mode BuildRun` 构建项目内的 Go 服务。它优先读取明确设置的 `S9A1_CREATION_CATALOG`，否则使用 `go-server/.work/catalog/characters.json`。`SyncOrigin` 沿用原仓库更新流程并定位现有 Go 源码的 Git 根；真实同步需要配置该源码仓库的 `origin`。发布包的同名入口根据已装二进制启动。

`StoppedDataBackup` 接受 `Work` 内已创建的 PostgreSQL 备份目录。部署前的两次只读复核沿用原有锁和失败返回，通过后才继续构建或启动。源码与发布包通过 `release-manifest.json` 区分，源码管理工具可构建 Go 并原子安装服务端，发行包从当前版本加载配套管理器。`-Dotnet` 可指定构建 Windows 管理界面的 SDK 路径。[启动辅助脚本](../go-server/tools/launcher-runtime.ps1) · [归档工具](../go-server/tools/postgres/save_archive.py) · [发布脚本](../go-server/tools/publish.ps1)

当前 Windows x64 发布包 `Serve100-Go-native-20261123.zip` 为 422,414,592 字节。包内有原生 Go 服务、4 个 Go 工具、配套管理界面、Go 从原始 PVF 生成的玩法与 GM 目录，以及 PostgreSQL 空服种子。重新打开成品 ZIP 后逐项复核了 375 个文件的长度和 SHA-256，加上清单共 376 项。整包 SHA-256 为 `D4732DB606ADC9F39BB33FC3783075BF585EA45BC5EE1EE83577AC17146ED11A`。[本机发行包](../go-server/.work/publish/Serve100-Go-native-20261123.zip) · [校验文件](../go-server/.work/publish/Serve100-Go-native-20261123.zip.sha256)

从成品包提取的 SQL 已在空 PostgreSQL 库执行，回读到 v16、`local` 账号、1,000,000 点券、0 个角色。收据保留原版的五个字段，`Build` 与包内服务文件生成的 UUID 一致。同一份服务程序再次产生的 SQL 摘要相同。上一版 Go 发行包的 v15 种子也已在隔离库升级到 v16，保留原发行账号，并可通过包内的 `import-save.exe` 重复导入原版 SQLite 到另一账号。[存档与收据](../go-server/internal/storage/README.md)
