# S9A1 全量服务端重构方案

2026-11-22 评审稿

**可以把当前 S9A1 的自有服务端全量迁到 Go 和 PostgreSQL。** 建议以一个 Go 服务端进程、一个 PostgreSQL 数据库起步，拟在项目内的 `go-server/` 开发。首个可玩里程碑是两台电脑、两个账号、同城互见。最终要做到一台全新的服务机仅凭 Go 服务及配套工具、匹配的原始资源和 PostgreSQL，就能准备资料、开服、运行当前快照中已有的正式玩法、管理玩家并恢复存档。

范围以本次固定的上游快照为准，包括已有正式入口、单人玩法、配置开关、资源与日常操作。新增联机能力单独验收账号隔离、共享城镇和组队副本。当前源码有 672 个服务端 C# 文件和 559 个测试 C# 文件。已按上游 72 个不同功能编号、正式路由装配引用的 67 个模块类和 28 份模块说明编成逐项清单。2026-11-23 已开始实施，补录了正式配置下的 151 个入站路由和实测性能基线，采用自有启动器加认证网关区分远程账号。 [全量迁移清单](全量迁移清单.md) · [实施进度](实施进度.md)

## 现有对外交互字段冻结

按项目要求，游戏客户端、启动器、资源工具、GM 和其他已有调用方使用的请求与响应字段全部冻结。Go 与 PostgreSQL 可以改变内部表示，对外继续使用原字段及其含义。未知字段沿用原有读写、校验或拒绝规则，保留位保留原用途。遇到必须新增、删改或重新解释对外字段才能实现的需求，先列明涉及的调用方、证据和可行的兼容方案，交由用户判断。

| 容易出现差异的地方 | 实现与验收依据 |
| --- | --- |
| 线上字节 | 固定方向、消息编号、帧头、字段顺序、位宽和符号、字节序、长度单位、编码、校验及压缩规则。保留缺省、空值、零与特殊标记各自的行为。角色名按原有 GB18030 规则处理，增加中文名称的字节长度边界用例。 [传输帧](../s9a1/Docs/Protocols/Frames.md) · [角色报文](../s9a1/Server/src/Serve100.Protocol/LocalEntryPackets.cs) |
| 回包顺序和时机 | 按同一操作核对成功、拒绝、重复请求的完整包序和触发条件。例如徽章合成先提交，再发成功应答 `ACK256`，最后发背包快照 `N13`。客户端收到成功应答时会扣界面材料，先刷快照有让界面再次扣减的风险。 [徽章合成协议](../s9a1/Docs/Protocol.md) |
| 工具和文件接口 | 固定已有命令行参数、配置键、JSON 字段名与类型、文件位置、就绪与退出语义，以及 GM 进程间请求和返回值。旧启动器读取 `runtime/next-ready.json`，还核对宿主文件、PID 和进程启动时间。Go 版的接入须保留这些值的真实含义。 [启动器就绪检查](../s9a1/ClientTools/LauncherUI/LauncherServerControl.cs) · [服务端命令入口](../s9a1/Server/src/Serve100.Host/Program.cs) |
| 客户端版本和资源 | 本次解压的 `DNF.exe` 为 `37.8.13.0`，SHA-256 以 `C1B772AC` 开头，与当前启动器登记一致。上游协议文档也引用了以 `AF044678` 开头的另一份 EXE。采纳字段结论前核对适用客户端、配套启动工具和实际 PVF。 [启动器文件登记](../s9a1/ClientTools/Launcher/ClientFileVerification.cs) · [协议依据](../s9a1/Docs/Protocol.md) |

每次迁移一条玩家操作，先锁定对应的独立样本。旧服与 Go 使用相同输入、资源和等价的独立测试存档，对照固定部分的原始字节、完整包序和数据库结果。时间、会话序号等动态值按各自的生成规则及前后关系核验，校验值按该帧实际内容复算。半包、粘包由公共传输测试覆盖，玩法按实际影响验证业务拒绝与提交后断线重连。涉及界面行为的流程再用匹配原客户端复验。 [测试口径](../s9a1/Docs/Testing.md)

## 实施顺序和验收条件

| 阶段 | 实施内容 | 通过条件 |
| --- | --- | --- |
| 0 · 固定版本，测出现状 | 记录上游源码、解压客户端、现用启动工具与 PVF 的版本或摘要。建议用本地 Git 保存源码基线。能与上游核对时记录提交号，否则标记为本地导入快照。用一次登录、进城、移动、拾取建立协议样本和性能基线。 | 能复现同一条单人流程，拿到全量构建、改单文件构建、冷启动、热启动和操作延迟的实际数字。 |
| 1 · 验证异机接入和账号身份 | 先在原频道和游戏报文、既有工具接口及原端点约定下，验证两段连接如何可靠归属到已认证账号。如需额外凭据，仅在独立于原协议的接入通道中验证其可行性。多人状态也要找到当前客户端已有的通知格式和消费依据。同步核对普通副本可提供的战斗输入。 | 两台电脑分别从原客户端进入同一服务，各自的频道和游戏连接都能归属到正确账号。第二人进入后第一人仍在线，同账号重连后旧连接的命令被拒绝。仅凭来源 IP 无法通过账号归属验收。 |
| 2 · 双人同城和重登 | 接入 PostgreSQL，完成账号、角色、选角、位置和城镇可见范围。实现同区域玩家进入、移动、离开的通知。接入第一批 PVF 数据。 | 用两个已完成教学的角色验证同城互见、移动、离开和重登，重启后核对角色、归属和位置。另用新角色验证首次选角按资源进入开场教学。 [现有开场流程](../s9a1/Docs/Modules/Entry.md) |
| 3 · 资产和角色成长 | 依次迁移背包、装备、钱包、仓库，再迁技能、任务、商店和邮件。给每笔资产变化明确归属、版本和重复请求处理方式。 | 拾取、穿戴、扣款、交任务的结果可逐笔对账。重复请求、提交后掉线、重启均不会重复发钱、发物或串号。 [资产规则](../s9a1/Docs/AssetRules.md) |
| 4 · 打通一个普通双人副本 | 实现邀请、入队、共同进图、换房、怪物状态、死亡、掉落和结算。每个实例由服务端统一维护状态，先为一个普通副本建立有依据的击杀判定，再扩到其他副本。 | 两人正常操作能打完同一场，看到一致的房间进度和掉落，每名符合条件的成员只领一次。覆盖一人掉线和重复领奖。另验新角色从开场教学正常打到回城。 [现有战斗信任范围](../s9a1/Docs/DungeonEventRules.md) |
| 5 · 完成其余正式玩法 | 按清单完成专项副本、决斗大厅与 AI、装扮宠物、阿拉德探险记、命运的抉择等。风暴、红玉、智慧、无相和洞察分别验证其入场、进度、次数及结算。原本单人限定的模式按原规则验收。 | 每个已有正式功能能找到 Go 入口和对应验证，缺少证据的玩家可见行为列明状态。同一套角色连续完成城镇、消耗、战斗、领奖和重登，跨模块存档可对账。 [全量清单](全量迁移清单.md) |
| 6 · 完成资料工具、运维与发布 | 收齐 Go 资源读取和规则目录，对接启动器的准备、就绪、停服与 GM 操作。适配一键启动和版本化发布，区分日常增量编译与正式发布校验。相关能力从阶段 0 起随玩法逐批建设。 | 在全新服务环境从匹配原始资源和空 PostgreSQL 开服。实测 GM 授权、离线邮件恢复、关服和重新启动。原客户端能用配套工具正常连接。 |
| 7 · 导入演练、容量验收与切服 | 旧档试导从阶段 2 开始。最终用同硬件、同资源及等价玩法复测性能，在约定的同时在线人数和活动负载下压测。做停写、最终导入对账、恢复及回退演练。 | 所有原有正式入口都有结论，约定的单人和多人场景通过，旧档对账一致，新服能从备份恢复，正式玩家请求全程由 Go 处理，才退役旧 C# 在线服务。 |

异机接入需要同时处理三个限制。当前启动脚本固定了本机地址和端口，新游戏连接会取消现有会话，数据库还约束账号必须为 `local`。账号与会话隔离可在新服务内部实现。原端点约定下的异机连接，以及启动器对 `Serve100.Host.dll` 的就绪检查，均需用真实调用方验证兼容方式。原包确实无法表达的能力在本阶段列出，相关玩法单独评审。 [启动脚本](../s9a1/ClientTools/Start-Client.ps1) · [会话接入](../s9a1/Server/src/Serve100.Host/LocalEntryModule.cs) · [数据库约束](../s9a1/Server/src/Serve100.Infrastructure/Storage/SqliteSchemaMigrations.cs) · [启动器就绪检查](../s9a1/ClientTools/LauncherUI/LauncherServerControl.cs)

副本工作量取决于服务端能判定哪些战斗结果。旧端允许本地客户端计算伤害和怪物血量。若现有输入不足以判定一次击杀，先明确缺少的动作或状态能否可靠取得，再决定该副本的实现范围。自动回放核对包和状态，两台电脑上的画面与操作按项目约定由用户实机验收。 [战斗事件规则](../s9a1/Docs/DungeonEventRules.md)

## PostgreSQL 和旧存档如何衔接

1. **账号隔离从第一张表开始。** 账号、角色、账号仓库和钱包分别记录归属。数据库内部主键与原协议角色标识显式映射，已有角色号和物品实例 UID 在导入、穿戴及重登后仍须一致。按账号管理当前有效会话，按角色或资产版本校验写入。涉及双方的资产变更在同一个数据库事务内完成，按固定顺序取得双方记录的锁。 [资产身份规则](../s9a1/Docs/AssetRules.md)
2. **把玩家看到的成功结果和入账结果对齐。** 数据提交成功后再发布状态、回复客户端。包序号按原会话规则处理，跨连接的领奖资格以持久化业务记录核验。提交结果不明时从数据库恢复，重试按该操作原有的应答、拒绝或同步规则处理。保留原物品 UID、原始属性字节、未知存档字段及历史领取记录。 [存储模块](../s9a1/Docs/Modules/Storage.md) · [提交与响应顺序](../s9a1/Docs/ConcurrencyAndLatency.md)
3. **先用一致性备份演练导入。** 独立导入工具按旧库的模块版本识别历史结构，以原升级链生成的样本作对照，将旧 `local` 明确映射到一个指定账号。核对角色、金币、物品 UID 与原始属性、快捷键、任务进度和奖励记录，再用导入角色实际重登。正式切换时冻结旧服写入，从最终备份重做导入与对账，然后开放新服。
4. **按新服是否已有玩家写入来回退。** 开放写入前可恢复原 SQLite 服务。开放写入后优先回退到已验证兼容当前 PostgreSQL 数据的服务版本。若必须退回 SQLite，先迁回新增数据并对账。 [旧端维护约定](../s9a1/Docs/OfflineMaintenance.md)

## 何时可以宣布全量完成

1. **范围可核对。** 上游已启用的玩法和操作入口在 Go 版找到实现、协议或操作记录及适用的存档证据。已由原客户端验证过的主要玩家流程在新版本复验。对历史上仅观察、测试专用或依赖外部组件的能力，按原有可用范围记录。影响约定玩法的缺口仍算待完成。 [迁移清单](全量迁移清单.md)
2. **联机可复现。** 两个真实账号能同城、组队打完所选普通副本并各自结算。重登、旧连接迟到和重复请求已有结果。局域网单服、两名玩家是首轮假设。正式容量、可接受的响应时间和构建目标在取得阶段 0 基线后约定，并在全量版本压测。
3. **旧服可退役。** 干净安装、匹配资料准备、完整存档导入、玩家操作、管理及备份恢复均走新系统。SQLite 只作为离线导入源，旧 C# 供开发时对照。首次正式切换前要定下原 `local` 存档的归属账号和新服已写入后的回退方案。
