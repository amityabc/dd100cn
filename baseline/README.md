# 旧 C# 服务端性能基线

在同一台 Windows 主机上，用原 S9A1 服务端、匹配的客户端 `Script.pvf` 和独立 SQLite 存档完成了 Release 构建与原生 TCP 测量。SDK 为 10.0.404，正式构建成功，零警告、零错误。每个运行实例使用自动分配的回环端口，全部通过本实例的停服文件关闭。版本、源文件摘要、资源哈希及分位数见[实测结果](results.json)。

| 场景 | 实测 |
| --- | --- |
| 原 `Server/BUILD.ps1` 全量构建，项目内空 NuGet 缓存，含依赖还原、全部工程和产物校验 | 77.175 秒 |
| 同一正式入口无修改，复核并复用已验证的构建 | 6.242 秒 |
| 仅 Host 及依赖，新的开发构建输出，复用依赖包 | 21.522 秒 |
| 开发构建无修改 | 2.947 秒 |
| Game 中一条实现代码变动，保持公开接口相同，增量编译到 Host | 6.416 秒 |
| 新进程从启动到发布本进程的 `next-ready.json`，空 PVF 准备缓存 | 70.354 秒 |
| 第二个新进程读取同一份 PVF 和准备缓存，启动到就绪 | 13.732 秒 |

冷启动耗时最多的两个上游阶段是 `QualityAndMail` 24.837 秒和 `DungeonDrops` 18.568 秒。热启动报告 274419 次准备缓存命中、13 次未命中。启动计时从创建服务进程开始，轮询就绪记录的间隔为 25 毫秒，未清理 Windows 文件系统缓存。构建与启动各取一次，此轮结果用于同机工程比较。

## 原生请求延迟

下表取热启动的新进程。使用本机 TCP，一条连接按序发请求，每项先预热 1 次，再取 100 次完整回包。`C679` 的空角色探测只在当次 `C8` 列表之后执行。分位数使用最近秩。

| 操作 | P50 | P95 | P99 |
| --- | --- | --- | --- |
| C8 取得空角色列表 | 12.818 ms | 15.435 ms | 16.655 ms |
| C679 空角色探测及其既有拒绝应答 | 8.223 ms | 10.078 ms | 12.203 ms |
| C1715 原生时钟回显 | 7.386 ms | 9.102 ms | 10.064 ms |
| C35 保存城镇位置，紧跟 C1715，至收到后者的完整回包 | 23.083 ms | 25.510 ms | 26.590 ms |

建角使用原生 C5 成功回包和 N2 名单投影。角色通过旧端支持的 C143 跳过开场教学，随后重新选角并完成两次 C120 城镇同步。该次从请求角色表到城镇就绪后的回显为 297.024 ms。C35 没有独立成功应答，故单列“移动加回显”的联合耗时，并回读 SQLite 确认 101 次坐标更新分别递增了角色版本。这里的 TCP 请求由测试程序生成，界面帧率、正常击杀后的拾取耗时及真实客户端画面仍待对应场景实测。

建角成功后的 SQLite 一致性备份保存在本次工作目录 `.work/fixtures/v35-character.sqlite3`，包含 ID 为 1 的「基线角色」，已通过 `PRAGMA integrity_check`。数据库导入测试读取这份副本。旧服实发的频道、登录及空角色协议样本见[协议对照](../go-server/testdata/protocol/legacy-empty.json)。

## 复测

从项目根目录运行以下命令，`$sdk` 指向可满足 `s9a1/Server/global.json` 的 `dotnet.exe`，`$python` 指向 Python 3.11 或以上版本。选择尚未使用的工作目录，以便区分冷构建和已有缓存。启动和测试均不操作游戏界面。

```powershell
$sdk = (Get-Command dotnet.exe).Source
$python = (Get-Command python.exe).Source
$run = Join-Path $PWD ('baseline/.work/' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
& $python -B baseline/measure_build.py --sdk $sdk --work $run
& $python -B baseline/measure_runtime.py --sdk $sdk --work $run
```

结果写入所选目录的 `results.json`。构建脚本在项目内复制纯上游源码并建立隔离 Git 快照，正式构建调用上游 `Server/BUILD.ps1`。开发增量修改位于隔离副本，计时后恢复。运行脚本只读游戏资源，使用独立配置、数据库与资源缓存。换新的工作目录时会重新下载 NuGet 依赖。

## Go 候选版对照

同机使用相同请求、顺序和回包边界测得 Go 端 C8、C679、C1715、C35 加 C1715 的 P95 分别为 2.569、0.421、0.402、4.427 毫秒。位置操作已在 PostgreSQL 回读 101 次版本增量。首批 Go Host 从空编译缓存构建用时 22.281 秒，原样重建 0.925 秒，修改一处玩法后重建 2.165 秒。两边构建所含功能随迁移进度有差异。这些单连接数据也与多人同时在线的容量分开记录。[Go 原始结果](go-results.json) · [已覆盖流程](../docs/实施进度.md)

从项目根目录用 `python -B baseline/measure_go.py --go <go.exe 路径>` 可在隔离副本重测 Go 构建。运行中的 Go 实例可按开发说明重测入口与移动，一项使用空账号，另一项使用已完成教学的隔离角色。[运行与复测](../go-server/README.md)

2026-11-23 在 148 个游戏入口和 3 个频道入口均接入后，再用隔离副本测得 Go 游戏服务空编译器缓存构建 22.974 秒、原样重建 0.801 秒、修改一处玩法后重建 2.387 秒。旧 C# Host 开发构建的同类单处修改为 6.416 秒。以上各取一次，Go 的计时范围是服务程序，不包括离线 PVF 准备及 Windows 工具打包。[本轮构建数据](go-results.json)

补齐特殊副本、翻牌收据回读、资源倍率和管理工具后，另取一份隔离源码重复相同三项测量，依次为 17.032 秒、1.052 秒、3.172 秒。两次都从已有依赖包开始，冷构建清空的是 Go 编译器缓存。[构建复测数据](go-results.json)
